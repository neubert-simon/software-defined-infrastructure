> We continue our exercise series ??? by adding a Cloud-init configuration:

Follow [Figure 1106, “Terraform triggering Cloud-init”](https://medieninformatik.cloud/sdi_cloudProvider_cloudInit.html#sdi_cloudProvider_cloudInit_terraformInterfaceCloudinit) and [Figure 1106, “Terraform triggering Cloud-init”](https://medieninformatik.cloud/sdi_cloudProvider_cloudInit.html#sdi_cloudProvider_cloudInit_terraformInterfaceCloudinit) to create simple web server.

```

```

With respect to [Figure 1112, “Watch out for your enemies!”](https://medieninformatik.cloud/sdi_cloudProvider_cloudInit.html#sdi_cloudProvider_cloudInit_watchOutForBadGuys) inspect the output of `journalctl -f` on your own server for a while. 
Then modify your current sshd configuration:

- Read the [sshd_config(5) - Linux man page](https://linux.die.net/man/5/sshd_config)
- Disallow [ssh](https://medieninformatik.cloud/glossary.html#glo_ssh) password based logins
- Disallow root login altogether
- Create a user devops eligible for both [ssh]([ssh](https://medieninformatik.cloud/glossary.html#glo_ssh)) login and sudo execution.

On success the following sequence should be possible:

```
$ ssh -v devops@95.217.154.104
...
debug1: SSH2_MSG_SERVICE_ACCEPT received
debug1: Authentications that can continue: publickey ❶
debug1: Next authentication method: publickey
...
Last login: Sun May  5 19:21:12 2024 from 217.245.243.187
devops@hello:~$ sudo su -
root@hello:~# hostname
hello
```

- password is not among the list of allowed authentication methods.
- User devops may execute **sudo** commands by virtue of his membership in group sudo.

On contrary ssh root login must be prohibited:

```
$ ssh root@95.217.154.104
root@95.217.154.104: Permission denied (publickey).
Read the cloud-init documentation and/or related tutorials to:
```
